# AirGrid Phase 01B: Secure Authentication & User Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement production-grade, secure user authentication, Argon2id password hashing, HttpOnly server-side cookie sessions, CSRF protection, rate limiting, and role-based access control (RBAC: Administrator, Network Engineer, Viewer) with an editorial-themed React login frontend, without disrupting Phase 00 foundations or the Phase 01A landing page.

**Architecture:** A robust server-side session authentication system within the FastAPI modular monolith using PostgreSQL-backed `user_sessions` and `users` tables. Cookie-based authentication (`HttpOnly`, `SameSite=Lax`) paired with Anti-CSRF double-submit / signed tokens for mutating operations. React frontend incorporates an `AuthContext` provider, `ProtectedRoute` route guards, real API communication, and a minimalist editorial login interface adhering to the Phase 01A off-white/copper design language.

**Tech Stack:** FastAPI, SQLAlchemy 2.0 (asyncpg / psycopg), Alembic, Argon2id (`argon2-cffi`), Pydantic v2, Pytest, React 18, React Router v6, Tailwind CSS, Lucide React, Playwright CLI.

**Spec:** Phase 01B User Prompt & System Architecture Specification.

## Global Constraints

- Never store session secrets, tokens, or plaintext passwords in browser localStorage or sessionStorage.
- Use Argon2id for password hashing with secure parameters (m=65536, t=3, p=4 or argon2-cffi defaults).
- Session tokens in cookies must be cryptographically random (min 32 bytes URL-safe), and only their SHA-256 hash stored in PostgreSQL.
- Server-side RBAC must strictly authorize: `administrator`, `network_engineer`, and `viewer`.
- Safe generic error messages on authentication failure: "Invalid email or password" (HTTP 401).
- No default credentials or open administrator registration; provide a secure CLI/startup bootstrap mechanism.
- Preserve all existing Phase 00 endpoints, models, tests, and Phase 01A landing page assets without disruption.
- No network scanning, ML training, speed tests, or Phase 02 features.

## Review Focus

- Missing or invalid CSRF token on mutating requests (POST/PUT/DELETE) must return HTTP 403 Forbidden.
- Session cookie expiration must reject subsequent requests with HTTP 401 and trigger frontend re-authentication.
- Rapid successive invalid login attempts must trigger rate limiting (HTTP 429 Too Many Requests) per IP/email.
- Role boundary violations (e.g. Viewer trying to create a user or delete an AP) must return HTTP 403 Forbidden.
- Unauthenticated browser navigation to `/dashboard` or internal routes must redirect to `/auth/login` while preserving return path.
